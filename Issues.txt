  [!] AND THE REASON THE BUILD NEARLY DID NOT FIT
        Shortening all that text pushed block B twenty-five bytes past its
        ceiling, which made no sense - the strings got SMALLER. Two real bugs in
        the dictionary fitter were hiding behind the slack:

        1. Blocks B and D are repacked into separate extents, but the fitter was
           handed the SUM of their room as one ceiling. It happily spent block
           D's two thousand spare bytes on block B, which cannot reach them.
           One limit per block now.

        2. Demoting an entry out of the cheap two-byte bank costs a byte at
           EVERY reference, but the victim was chosen by how often the FIXED
           strings used it - block B's use of it counted for nothing. So the
           fitter kept demoting entries block B leans on hundreds of times.
           Demotion is priced across every block now.

        Block B was at 243 spare before this round and is at 3,213 now. The
        second bug had been quietly costing about three thousand bytes all
        along. The rescue pass also adds its entries one at a time and keeps
        what fits, instead of giving up on the first combination that does not.

        Also: MAX_ENTRIES was 765 where the 768-slot table holds 766 - slot()
        steps over the two escape markers, so index 765 is slot 767. The last
        slot had never been used.

        "Sell the <NAME:0301>?" is not nine cells wide. <NAME:sWW> pads UP to WW

        item it is is not known until the game runs. My width model counted the
        field as its declared one cell; "Wooden Staff" is six. So the line is
        really 11.5 cells, and the three cells of padding round one added took
        it to 14.5. Half a cell past the fourteen-cell window is the right
        border, and that is the border that disappeared.

        The Japanese sized these lines so the longest name just fits - there is
        nothing spare to pad, and padding can only overflow. The padding is off
        every line in those windows that carries a <NAME> field: B0334 B0338
        B0351 B0361 B0378 B0386 B0388.

        tools/check_cover.py now models a field at its WIDEST rather than its
        declared width, and flags with !! any line that could run past the
        window. It reports 14.5 cells for the string as it was, and 11.5 as it
        now is, so this particular mistake cannot come back unseen.

        This also explains the "Thank you kindly." border bite properly. It was
        the same half cell over the edge, from the same padding pass.

        and a HALF cells where the Japanese is eleven - the padding pass only
        ever ADDED width, so a line that was already too wide went straight past

        fourteen cells wide and the line was only 11.5, so on the geometry alone

        matching the Japanese width exactly is what fixed it. That is the rule
        to hold to: not "under fourteen cells" but "the width the Japanese had".

  [x] Resetting causes garbage instead of the company logo - EMULATOR, NOT ROM

        Two things from chasing it that are worth keeping. First, a diff of our

        If it ever needs revisiting, tools exist to stage the patch set one step
        at a time and find which one a symptom belongs to.

Playthrough issues
==================

DONE - text that would not clear
--------------------------------
One bug, four symptoms. Menu and shop windows are never cleared between one
string and the next; they did not need to be, because every Japanese glyph was
a whole cell, so each line covered the line before it and left the cursor where
the next string expected it. Half-width English covers half as much per
character. Every line in these windows is now padded back to the width the
Japanese filled. See "Covering, not just fitting" in docs/translating.md and
`python3 tools/check_cover.py`.

  [x] Drop Item menu option leaks an m when canceled out of (Use item)
        the five submenu headers were 4 to 5 cells and the Japanese were all 5;
        "Drop Item" is 4.5, so its last half-cell survived "Use Item". All five
        padded to 5 cells.
  [x] Shop text is writing over itself
        "Welcome to my shop!" covered 9.5 of the 14 cells the Japanese filled,
        so the menu that follows it started mid-line. Padded to 14.
  [x] Item Storage (in the Barracks) is not clearing properly
  [x] Appraiser as well
  [x] Temple: text not clearing
        52 strings across the appraiser, antiquary, shop, storage, temple and
        inn padded back to their Japanese widths.
  [x] Shop numbers don't clear properly when scrolling through the items
        an engine bug, not a text one. $90:97C6 blanked `width + $A8 - 8` WHOLE
        cells before the digits, which came to `width` exactly while a digit was
        a whole cell too. With half-width digits the field shrank as the number
        grew, so a longer number no longer reached over a shorter one. NUMPAD in
        build/hw_patch.py counts the digits' cells instead, and the field is
        `width` cells again whatever the value. Fixes every number in the game.
